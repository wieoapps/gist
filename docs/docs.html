gist-server documentation

A technical tour of every service gist-server can compile into. If you prefer a more narrative-driven onboarding, check out the OPERATORS LEDGER GUIDE, or jump straight to the CONFIG GENERATOR to build a config.json interactively.

This document is a reference: one section per service, each covering its real exported Go API (verbatim signatures, not paraphrased), what it costs to configure, and what it doesn't do.

The running example throughout is orderflow, a small order-processing backend — Order and OrderItem rows in MySQL, a payment-gateway call, order search, receipt storage, a lifecycle state machine, a nightly reconciliation job, and an event bus. It exists purely to give every service a concrete call site.

Prerequisites:

  • Go 1.27+
  • Docker (if you use gist-fixtures)

Wiring shape

Every example below assumes the same servicesGroup pattern — a plain struct whose fields are DI-tagged to match a service's config id:

Go
type ServicesGroup struct {
    OrdersDB *gistmysqlclient.Service `name:"orders-db"`
    Search   *gistelasticsearchclient.Service `name:"order-index"`
    Receipts *gistgooglecloudstorageclient.Service `name:"receipts"`
    // ...one field per service instance you actually use
}

gist.NewApp builds one ServicesGroup (or several, if different handler groups need different subsets) via reflection over these tags, and hands it to every EndpointHandler, RegisterTriggerFunc, RegisterScheduleFunc, etc. below as their first parameter. None of the examples redeclare this struct — assume sg ServicesGroup throughout.

00

gist-server command line

The gist-server binary has three independent modes, selected by which flags are set. Flag list verbatim from gist-server -h.

Normal run — what gist.NewApp invokes for you

Shell
gist-server -admin-socket <path> -callback-socket <path> -config <path>
FlagDescription
-admin-socket <path>Path to the admin gRPC unix socket. Your own process registers its endpoint/trigger/schedule handlers here.
-callback-socket <path>Path to the callback gRPC unix socket — the other half of the handshake; gist-server calls back into your process here.
-config <path>Path to your config.json.

You won't usually type this yourself: gist.NewApp reads config.json's own top-level "gist-binary" field for the binary path, generates both socket paths per run, and execs this exact command. Only reach for it directly when you're driving gist-server outside the SDK (debugging, a non-Go customer process).

Scaffold a new Go project

Shell
gist-server -new-project orderflow
gist-server -new-project orderflow -project-path ./somewhere/else
FlagDescription
-new-project <name>Generates a starting go.mod + main.go; <name> becomes the Go module name. Refuses to run if a go.mod already exists at the target path.
-project-path <dir>Where to scaffold it. Defaults to ./<name>.

Generate a starting config.json

Shell
gist-server -generate-config gist-api-server,gist-mysql-client -out config.json
gist-server -generate-config all -out config.json
FlagDescription
-generate-config <kinds>Comma-separated service kinds, or all. Valid kinds (every service in this doc except gist-custom, which has no fixed schema to scaffold): gist-api-server, gist-auth, gist-elasticsearch-client, gist-fixtures, gist-google-cloud-storage-client, gist-http-client, gist-http-server, gist-mysql-client, gist-postgres-client, gist-pub-sub-client, gist-rabbit-mq-client, gist-redis-client, gist-reverse-proxy, gist-scheduler, gist-state-machine.
-out <path>Output path. Default config.json.

Every field of every requested kind's real Config struct is written out with a placeholder value — generated by reflection over the actual struct, not hand-maintained, so it never drifts from the real fields. The output is a starting point to fill in, not a finished config.

Combining scaffold + config

Shell
gist-server -new-project orderflow -generate-config gist-api-server,gist-mysql-client

Scaffolds the project and writes config.json into it in one call. If -out was left at its bare default, the config lands at <project-path>/config/config.json specifically — exactly where gist.NewApp already looks by default (the CONFIG_FILE env var, defaulting to ./config/config.json) — so the scaffolded project needs no .env adjustment to find it.

Logging

Always on

Not a configurable service — always on, package-level, no config entry of its own.

Go
logging.Info("order approved", map[string]any{
    "order_id":    order.ID,
    "customer_id": order.CustomerID,
})
logging.Error("charge failed", map[string]any{
    "order_id": order.ID,
    "error":    err.Error(),
})

Swallowed handler errors (anything reaching gist-api-server's BubbleUpErrors boundary) carry a v4 UUID trace ID in both the client response and the log line — search logs by that ID rather than by timestamp when a customer reports "order 1001 failed" and you need the exact failure, not a guess at which log line it was.

gist-api-server

Public HTTP listener + endpoint registry. You declare routing/doc metadata in endpoints.json (see below) and bind a Go handler to each id separately, at startup, via Attach. An id with no handler serves as 501 Unimplemented automatically, not a startup error — declare the shape of an endpoint before it's real.

This instance's own listener is always plain HTTP — there's no protocol/TLS config field, since the underlying net.Listen is never wrapped in TLS. Front it with HTTPS via a reverse proxy if you need that; docs.servers[] (in Full below) is exactly where you'd document that proxy's own URL for the OpenAPI spec, independent of this listener's own address.

API (package gistapiserver)

Go
func EndpointHandler[servicesGroup any, in any, out any](
    id string,
    expectedErrors []ExpectedError,
    fn func(sg servicesGroup, ctx context.Context, in in, output *out) error,
    mockData *out,
) *Handler[servicesGroup]

func Attach[servicesGroup any](serviceID string, handlers ...*Handler[servicesGroup]) gist.Option

in/out are plain structs; field tags drive both the OpenAPI schema and wire decoding — path:"id", query:"status", json:"items", plus required:"true", minLength/maxLength, pattern, minimum/maximum, and example (required if the instance's docs.enforce-example-data is on). mockData *out is a required parameter, not optional — pass nil explicitly when there's no mock, so "no mock configured" is a visible choice at every call site rather than an easy omission.

Go
type CreateOrderInput struct {
    CustomerID int              `json:"customer_id" required:"true" example:"42"`
    Items      []OrderItemInput `json:"items" required:"true"`
}
type CreateOrderOutput struct {
    OrderID int    `json:"order_id" example:"1001"`
    Status  string `json:"status" example:"pending"`
}

var CreateOrder = gistapiserver.EndpointHandler("create-order",
    []gistapiserver.ExpectedError{
        gistapiserver.InvalidArgument,
        gistapiserver.Internal,
    },
    func(sg ServicesGroup, ctx context.Context, in CreateOrderInput, out *CreateOrderOutput) error {
        order := model.Order{
            CustomerID: in.CustomerID,
            Status:     "pending",
        }
        if _, err := gistmysqlclient.SaveAutoClose(sg.OrdersDB, &order); err != nil {
            return err
        }
        out.OrderID, out.Status = order.ID, order.Status
        return nil
    },
    &CreateOrderOutput{ // mock, served on ?mock=true
        OrderID: 1,
        Status:  "pending",
    },
)

func AttachEndpointHandlers() gist.Option {
    return gistapiserver.Attach("orderflow-api", CreateOrder /* , GetOrder, ... */)
}

ExpectedError (package gistapiserver, prebuilt vars, one per gRPC-style status code): FailedPrecondition, InvalidArgument, OutOfRange, Unauthenticated, PermissionDenied, NotFound, Aborted, AlreadyExists, ResourceExhausted, Canceled, DataLoss, Internal, Unknown, Unimplemented, Unavailable, DeadlineExceeded — each with .WithMessage(fmt string, values ...any) ExpectedError and .WithoutMessage().

gist-auth

No API

OAuth provider (apple / gitea / google via goth/gothic), serving three fixed routes — begin, callback, logout — on its own listener. No client-side API exists at all: no injectable Service type, no way to read the authenticated identity from inside another handler, no session hook. This isn't an oversight to work around; it's the service's actual current shape — it's a complete, self-contained OAuth handshake, and today that's where its responsibility ends. If orderflow needs "which customer is this request from" inside create-order, that has to come from somewhere else (a bearer token your own middleware validates, an API key via gist-api-server's api-key field, etc.) — not from this service.

Only one instance per provider should be configured — provider registration is process-global, not scoped to the instance's own id.

Config: gist-auth-config

gist-fixtures

API

Boots a testcontainers-backed dependency (MySQL, Postgres, MariaDB, MSSQL, MongoDB, GCS emulator, Elasticsearch, RabbitMQ, a Pub/Sub emulator, Mailpit, or Redis) and seeds it, in one call, from tagged Go structs — no separate fixtures format, no testfixtures dependency.

Config, including every container type: gist-fixtures-config
JSON
"gist-fixtures": [
  {
    "id": "orderflow-fixtures",
    "enabled": true,
    "type": "mysql"
  }
]

API

Go
func GenerateFixtures(id string, rows ...any) gist.Option

Reflection reads three tags, ignoring json/example (those are for docs elsewhere, inert here): source:"schema.table" (required, panics if missing), db:"column", and join:"..." on a []OtherStruct field to recurse into it as a relation rather than treat it as one column — same model structs gist-mysql-client already uses work here unchanged:

Go
gistfixtures.GenerateFixtures("orderflow-fixtures",
    []model.Order{
        {
            ID:         1,
            CustomerID: 42,
            Status:     "pending",
            Items: []model.OrderItem{
                {
                    OrderID: 1,
                    SKU:     "WIDGET-1",
                    Qty:     3,
                },
            },
        },
    },
    []model.Customer{ // flat table, no join needed
        {
            ID:   42,
            Name: "Acme Co",
        },
    },
)

Multiple rows...any arguments in one call can freely mix joined and flat tables; unexported fields are skipped even with a db tag present.

Container types

id/enabled/delayed-start/wait-for/ image/host-port/restart-after apply the same way to every type (full descriptions in gist-fixtures-config); what follows per dialect is only the fields specific to it. None of them are strictly required by the code — every one is a nil-checked pointer field, and an unset one just falls back to the image's own default — but each dialect has fields worth setting for the container to do anything useful, which is what each dialect's own Minimal below sets.

restart-after tears a booted container down and boots a fresh one from the same fixture data, on a timer — 48h by default, since a long-running dev/test container is otherwise just as susceptible to memory growth or state drift as any other long-lived process. Every duration field across every service (delayed-start, timeout, restart-after, connection-ping, query-timeout, conn-max-lifetime-minutes, gist-api-server's timeouts.read/write/idle) accepts either a bare number in its own pre-existing unit (seconds, except conn-max-lifetime-minutes, which is minutes) or a unit-suffixed string — w/W, d/D, h/H, m/M, s/S — e.g. "restart-after": "2d" instead of "restart-after": 172800.

elasticsearch, pubsub, rabbitmq, mailpit, and redis containers have no init-script mount point, so their seed data is delivered by a live client call right after boot instead — same rows...any call, different table conventions per dialect. mailpit's is a single "messages" table: to (required — a row with none is skipped), from (defaults to fixtures@localhost), subject, body; each row is sent as one real SMTP delivery, so it shows up through the running container's own web UI/REST API exactly like a message a test sent itself would. redis's is a single "strings" table: key (required — a row with none is skipped), value (stringified, defaults to ""); each row is a real SET, sent over a hand-rolled RESP connection rather than a client library (SET is a three-line wire command, not worth a new dependency for).

Two ways to get the configured transition graph out (client side) - the structure itself, not any particular object's current state, since this service holds none. //   os.WriteFile("order-lifecycle.svg", []byte(svg), 0o644)

Your own process already owns whatever HTTP server it runs - unlike a framework that owns the only listener, mounting GraphSVG on a route is one handler, not a config field:

http.HandleFunc("/order-lifecycle.svg", func(w http.ResponseWriter, r *http.Request) {

    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)

    w.Header().Set("Content-Type", "image/svg+xml")
    _, _ = w.Write([]byte(svg))
