How it works.

Gist's whole model is to make infrastructure disappear from your application code. Your app deals in typed Go objects and callbacks — business logic, handlers, state. Everything ugly about talking to a database, a queue, or a bucket lives one process away, in gist-server.

┌──────────────────────┐
│ Your Go code         │
│                      │
│ Business logic       │
│ API handlers         │
│ State callbacks      │
│ Custom services      │
└──────────┬───────────┘
            │
      gistsdk API
            │
     local gRPC/IPC
            │
┌───────────▼──────────┐
│ gist-server          │
│                      │
│ HTTP/API             │
│ MySQL                │
│ PostgreSQL           │
│ Elasticsearch        │
│ GCS                  │
│ RabbitMQ             │
│ State machines       │
│ Scheduling           │
│ Logging              │
└──────────────────────┘

That split buys real advantages, not just tidiness:

  • — All your infrastructure lives in one place
  • — One config format for every service
  • — One process to watch — logs and metrics in one place
  • — A crash in a database driver can't take your app down with it
  • — The gRPC boundary means the server side isn't locked to Go

Your app starts it once, as a child process:

          Your Go application
                    │
                    │ imports
                    ▼
         github.com/wieoapps/gist
                    │
                    │ starts, as a subprocess
                    ▼
               gist-server
                    │
                    ▼
   api-server, mysql, postgres, elasticsearch,
   redis, pub-sub, rabbit-mq, http-client,
   http-server, auth, scheduler, state-machine,
   gcs, fixtures, load-balancer

Then every call is proxied straight through to the real thing:

        Your code
            │
            ▼
gist-elasticsearch-client
            │
            ▼
         rpcconn
            │
            ▼
          gRPC
            │
            ▼
       gist-server
            │
            ▼
      Elasticsearch

You only wire up what you use — one tagged struct field per service:

type Services struct {
    DB            *mysql.Service         `name:"database"`
    Elasticsearch *elasticsearch.Service `name:"search"`
    Storage       *gcs.Service           `name:"storage"`
    Logger        gist.Logger
}

Performance.

That extra hop has a real cost — measured, not guessed. Here's a single database lookup, direct versus through gist:

Direct call, same process       503,051 ns/op   (0.503 ms)
Through gist, one gRPC call     559,562 ns/op   (0.560 ms)
                                 ─────────────
Overhead                        +56,511 ns     (+0.057 ms, +11.2%)

Measured on a single MySQL point lookup, averaged over four 1000-query runs. There's no network involved either way — gist-server runs on the same machine, so this is one local unix-socket round trip, not a remote call.
